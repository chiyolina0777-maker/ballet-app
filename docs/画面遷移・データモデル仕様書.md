## 1. 全体方針

- 認証は LINEログイン のみ。メール/パスワード認証は実装しない。
- **閲覧はすべて未ログインで可能**。ログインが必要になるのは「フォロー」「観劇ログ記録」「設定変更」の操作時のみ(遅延ログイン方式)。
- 公演・ダンサー等のマスタは管理者のみ書き込み可能(Supabase service role)。一般ユーザーの書き込みは follows / company_follows / theater_logs / profiles に限定(RLSで強制)。
- すべての公開ページはSSRで描画し、OGP・構造化データを出力する(SEO要件)。

## 3. 画面仕様

### S1 ホーム `/`
- 表示: (a) ログイン時のみ「フォロー中の新着」= フォロー対象ダンサーの直近のキャスト発表・発売開始を時系列で最大10件、(b) 「今後の公演」= `performances.starts_on >= today` を開催日昇順で一覧(カード: 公演名/バレエ団/劇場/期間)。
- アクション: 公演カード→S3、新着アイテム→S3該当公演、検索ボックス→S2/S4。
- 空状態: 未ログイン時は新着枠の代わりに「推しをフォローすると新着が届く」訴求+人気ダンサー例。

### S3 公演詳細 `/performances/[id]`(最重要画面)
- 表示:
  - ヘッダ: 公演名、バレエ団、演目(複数の場合は上演順に「/」区切りで列挙)、劇場、期間、ステータス(発売前/発売中/終演)。
  - 発売情報: `ticket_sales` を日時昇順に列挙(種別ラベル+日時。未来の窓口は「発売開始 M/D HH:mm」、開始済みは「発売中」)。
  - **日別キャスト表**: `shows` を日時昇順に列挙。各行 = 日付・開演時刻・主要キャスト(`casts` の role_name: dancer名)。ログインユーザーのフォロー対象が含まれる行に「推し出演」バッジ。キャスト未発表の回は「キャスト未発表」表示。
  - 出典と免責: `source_url` へのリンク+「公式発表に基づく。変更の可能性あり」の注記。誤り報告リンク(mailto または フォーム)。
- アクション:
  - 「チケットを購入」→ S10(`/go/[performance_id]?src=web`)。
  - キャストのダンサー名タップ → S4(該当ダンサーの位置へスクロール・ハイライト。フォローはそこで行う)。
  - 各公演回の「観劇を記録」→ S7(未ログインなら S9 を経由して戻す)。
- SEO: title「{公演名} キャスト・日程 | {サービス名}」。構造化データ(Event)。

### S4 ダンサー一覧 `/dancers`(フォロー操作の起点)
- 表示: **バレエ団ごとのセクション**に分けてダンサーを列挙(セクション見出し=団体名。団体内の並びは階級順→かな順)。各行 = 名前・階級・フォローボタン。**セクション見出しにはバレエ団のフォローボタン**を置く(company_follows。「その他」セクションには置かない)。所属なしのダンサーは「その他」セクションに。
- 検索: 上部の検索ボックス1つで、ダンサー名・かな・バレエ団名を横断してインクリメンタル検索する(団体絞り込みUIは置かない)。団体名にヒットした場合はその団体の全ダンサーを表示、ダンサー名・かなにヒットした場合は該当行のみ表示。いずれもグルーピングを維持する。
- アクション: 「フォロー」トグル(未ログイン→S9経由で戻し、自動でフォロー完了まで進める)。フォロー完了時、初回のみ「LINEに通知が届きます」のトースト+友だち追加導線を表示。
- 備考: S5(ダンサー詳細)はフェーズ1では作らない。プロフィール・出演予定の詳細表示はフェーズ2以降。

### S6 マイページ `/me`
- 表示: 観劇ログ一覧(新しい順。日付/公演名/キャスト/座席/メモ冒頭)、集計(今年の観劇回数、最多観劇ダンサー トップ3)、共有用画像の生成ボタン(年間まとめ)。
- アクション: ログタップ→S7編集、公演名タップ→S3。

### S7 観劇ログ記録
- 入力の起点は必ず「公演回(show_id)」。日付・演目・劇場・当日のキャストはDBから自動表示し、ユーザー入力は 座席(任意テキスト)・感想メモ(任意)のみ。
- `is_public` は常に false(フェーズ1では公開機能なし。列のみ将来用に保持)。
- 一意制約 `(user_id, show_id)` に該当する場合は新規作成でなく編集画面を開く。
- 過去の公演回のみ記録可能(`shows.starts_at < now`)。未来の回にはボタンを出さない。

### S10 計測リダイレクト `/go/[performance_id]`
- クエリ: `src`(`line` | `web` | `share`)。
- 処理: click_events にINSERT(user_idはセッションがあれば付与) → `performances.ticket_url` へ302。ticket_url未設定なら S3 に戻しトースト表示。

### 管理画面(A1-A3)
- 認証(決定): 環境変数(`ADMIN_USER_IDS`)で管理者UIDを指定する。`profiles.is_admin` カラムは導入しない(管理者が複数・可変になったらフェーズ2で再検討)。一般UIとは別レイアウト。
- A2の入口は公演一覧(`/admin/performances`)。登録済み公演の状態(公演回数・販売設定・キャスト公開状況)を一望し、検索(公演名・バレエ団・期間)とステータス絞り込みを備える。各行から公演編集・キャスト入力へ遷移する。
- A2の入力フロー(最頻の運用作業。3分以内で完了できること):
  1. 公演作成(バレエ団・劇場はセレクト+新規追加、**演目は複数選択のタグ式**(performance_works。新規追加も同一画面から)、日程、チケット販売日時=種別ラベル+日時を複数登録(ticket_sales)、ticket_url、source_url)
  2. 公演回の一括生成(期間と曜日別(月〜日+祝)の時刻パターンから複数生成 → 個別編集。時刻未設定の曜日は生成しない。祝日の時刻は曜日設定より優先し、祝日判定は祝日マスタ/ライブラリによる)
  3. キャスト入力(公演回×役×ダンサー。ダンサーはインクリメンタル検索、未登録なら即時追加)
- キャスト保存時に通知キューへの登録を行う(§6)。「保存して通知」「保存のみ(下書き)」を分ける。

## 4. 画面遷移ルール

主要導線(遷移図は本書と併せて共有済みのものを正とする):

- LINE通知 → S3(ディープリンク。通知メッセージのボタンURLは `/performances/[id]?src=line&utm_...` 形式)
- S1 → S3 / S2 / S4
- S3 → S4(キャスト名タップで該当ダンサー位置へ。ハイライト表示)
- S3 → S10 → 外部チケットサイト
- S3 → S7(観劇を記録)
- S4 → S9 → S4(フォロー時の遅延ログイン。`redirect_to` パラメータで復帰先を保持)
- グローバルナビ: ホーム / 公演 / ダンサー / マイページ の4項目固定。

認証ガードの原則: 未ログインでガード対象操作をした場合、操作内容をクエリに保持したままS9へ。認証完了後に操作を自動再実行して元画面へ戻す(例: `/auth/line?redirect_to=/dancers&action=follow&dancer_id=xxx`)。

### フォロー完了までのフロー(友だち追加を含む)

通知(§6)は友だち追加済みユーザーにしか届かないため、フォロー導線は「フォロー成立」と「友だち追加」の2つを完了させて初めてゴールとする。

```
[S4 ダンサー一覧] 「フォロー」をタップ
      │
      ├─ ログイン済み ────────────────────────────┐
      │                                           │
      └─ 未ログイン                                │
           │                                      │
           ▼                                      │
      [S9 LINEログイン]                            │
        ・bot_prompt=aggressive                   │
          (同意画面に「友だち追加」を併記)      │
        ・redirect_to=/dancers                    │
          &action=follow&dancer_id=xxx            │
           │                                      │
           ▼                                      │
      [/auth/callback]                            │
        認証完了・profiles 作成/更新              │
           │                                      │
           ▼                                      ▼
      ┌─────────────────────────────────────────────┐
      │ follows へ INSERT(フォロー成立)            │
      │ S4 の該当ダンサー位置へ復帰・ハイライト     │
      └─────────────────────────────────────────────┘
           │
           ▼
      友だち状態を確認
      (LINEログインの friendship status API /
       webhook の follow/unfollow イベントを正とする)
           │
           ├─ 追加済み → トースト「LINEに通知が届きます」(初回のみ)
           │
           └─ 未追加 → トースト+友だち追加バナーを表示
                        「通知を受け取るには友だち追加が必要です」
                        [友だち追加ボタン(公式アカウントのリンク)]
                        ※閉じてもフォローは成立したまま。
                          S8(設定)にも未追加バナーを常設
```

- バレエ団フォロー(company_follows)も上記と同一フロー(タップ対象がセクション見出しのフォローボタンになり、INSERT先が company_follows になるだけ)。
- `bot_prompt=aggressive` を付けてもユーザーは友だち追加のチェックを外せるため、**追加は保証されない**。認証完了後の状態確認と、未追加時のバナー表示を必須とする。
- 友だち状態の追跡は、ログイン時の friendship status API に加えて、Messaging API の webhook(follow / unfollow イベント)で更新するのを正とする(ブロック・解除の検知のため)。保持先として `profiles.is_line_friend boolean default false` を追加提案(§5)。
- 通知バッチ(§6)は送信前に `is_line_friend = true` で絞り込み、未追加ユーザーへの無駄な Push(エラー)を出さない。

## 5. データモデル

テーブル定義・制約・RLSは `schema.sql` を正とする。ここでは関係の要点のみ。

```
companies ─┬─< dancers >─── follows >─── profiles(= auth.users)
           ├──────────< company_follows >── profiles
           └─< performances ─< shows ─< casts >── dancers
venues ────< performances          │
works ──< performance_works >── performances(演目は多対多・上演順付き)
                                   ├─< theater_logs >── profiles
                                   └─< notifications >── profiles
performances ─< click_events
performances ─< ticket_sales(販売窓口: 会員先行/一般発売など複数)
```

- 核は performances(公演) → shows(公演回) → casts(役×ダンサー) の三層。通知・記録・バッジ判定はすべて show を主語に行う。
- 「推し出演」判定: `exists (casts c join follows f on f.dancer_id = c.dancer_id where c.show_id = 対象 and f.user_id = 自分 and c.status <> 'cancelled')`。
- キャスト変更の扱い: 行の置換ではなく `status` 更新(`scheduled→changed/cancelled`)+新行追加。履歴が残り、変更通知のトリガーにもなる。
- チケット販売日時は `ticket_sales`(公演1:N)で保持する。`performances.sale_starts_at` は後方互換のため残置するが、発売通知のトリガーは `ticket_sales` の各行を正とする。
- フォローは2種類: ダンサーフォロー(`follows`)と**バレエ団フォロー(`company_follows`)**。バレエ団フォローは、キャスト未発表の公演でも発売通知を届けるための宛先になる(§6)。
- `casts.is_published`(下書き保存用)と `profiles.is_line_friend`(友だち状態。webhook の follow/unfollow で更新。§4フロー参照)は schema.sql に反映済み。`profiles.is_admin` は導入しない(管理者認証は環境変数方式に決定。§3参照)。
- **ミックスプログラム(複数演目の公演)の扱い(決定・v1.7改訂)**: 公演と演目は `performance_works`(多対多。上演順 `sort_order` 付き)で紐づけ、`performances.work_id` は廃止する。トリプル・ビルやガラは演目を複数登録する(演目未登録+公演名のみも可)。**キャスト行への演目紐付けは行わない**(A2-3の入力速度を優先。必要な場合は役名の自由記述「ボレロ: メロディ」等で運用)。演目別の観劇集計・検索はフェーズ2でこのデータをそのまま使う。

## 6. 通知トリガー(画面との対応)

| 種別 | トリガー | 宛先 | 通知内のリンク先 |
|------|---------|------|----------------|
| キャスト発表 | A2でキャスト保存(公開) | 該当ダンサーのフォロワー | S3(該当公演) |
| キャスト変更 | casts.status 変更 | 該当ダンサーのフォロワー | S3 |
| 発売開始 | ticket_sales.sale_starts_at の各行の前日9:00(Cron) | 主催バレエ団のフォロワー ∪ 出演ダンサーのフォロワー(distinctで1人1通) | S10(src=line) |

- **発売通知の宛先集合と重複排除**: 宛先は次の和集合を distinct したもの。
  ```
  recipients(ticket_sale) = distinct(
      company_follows.user_id  where company_id = 公演の主催バレエ団
    ∪ follows.user_id          where dancer_id in (公演の全showのcasts, status <> 'cancelled')
  )
  ```
  - バレエ団と出演ダンサーの両方をフォローしているユーザーにも**1通のみ**。
  - **ゲスト出演**(casts のダンサーの所属が主催と異なる)も casts 起点で同じ集合に入るため、そのダンサーのフォロワーにも届き、かつ主催バレエ団もフォローしていれば distinct により1通に収まる。
  - 最終防波堤として notifications の `unique(user_id, kind, ticket_sale_id)` が二重INSERTを拒否する(送信処理のリトライ時も安全)。
- キャスト発表・変更の通知は従来どおり**ダンサーフォロワーのみ**を宛先とする(バレエ団フォロワーには送らない。全公演のキャスト情報が届くとノイズが大きいため。反響を見てフェーズ2で再検討)。
- **送信タイミング(決定)**: 全種別(キャスト発表・キャスト変更・発売開始)とも**即時送信はしない**。A2の「保存して通知」やstatus変更は通知キューへの登録であり、送信は9:00/18:00の2バッチで行う。キュー登録後の取り消しは不可。
- 同一ユーザー×同日の複数イベントは1通に束ねる(ダイジェスト)。
- キャスト変更通知の宛先は該当ダンサーのフォロワーのみ(観劇ログは過去回のみ記録可能で「その回の観劇予定者」のデータは存在しないため。観劇予定の登録はフェーズ2で検討)。
- 二重送信防止は notifications の unique 制約で担保する。キャスト系(show起点)は `unique(user_id, kind, show_id)`、発売通知(販売窓口起点。show_idはNULL)は `unique(user_id, kind, ticket_sale_id)`。
- 送信方式の前提: 通知は LINE Messaging API の Push を自前の Cron から送信する。LINE公式アカウントマネージャーの「予約配信」はブロードキャスト/セグメント配信用であり、follows に基づく個別宛先の配信には使わない(LINE側での予約設定は不要)。
- **受信の前提: Push が届くのは、対象ユーザーが公式アカウントを友だち追加している場合のみ**。LINEログインで `line_user_id` を取得できても、友だち未追加ユーザーには届かない。したがってフォロー完了導線(S4)に友だち追加(LINEログインの bot_prompt=aggressive もしくは友だち追加リンク)を組み込み、S8(設定)に友だち状態の表示を置く。具体的なフローは§4「フォロー完了までのフロー」を正とする。
- Push の無料通数上限・従量料金はプランに依存するため、配信数の増加時はダイジェスト化(上記)とプラン見直しで対応する。

## 7. 非機能・その他

- 実装スタック(決定): Next.js(SSR)+ Supabase(DB/Auth/Cron)+ Vercel + LINE(Login / Messaging API)。
- 対応環境: モバイルブラウザ優先(利用の大半がLINEアプリ内ブラウザ経由と想定。LIFFは使わず通常のWebで開く)。
- 表示速度: S3はSSR+CDNキャッシュ(キャスト更新時にrevalidate)。
- 個人情報: line_user_id は表示・エクスポートに含めない。退会時は profiles ごとcascade削除。
- 命名・用語: 「公演」=performance、「公演回」=show、「キャスト」=cast。UI文言もこの対応で統一する。
